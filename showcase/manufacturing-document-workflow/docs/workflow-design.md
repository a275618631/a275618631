# 文件版本工作流：設計與責任

## 情境

虛構企業 ALPHA 的製程規格文件出現新版。目標是讓版本比對與審核更可追溯，同時避免模型看到不在授權範圍內的內容。

## 工作流

1. 接收新版事件，驗證事件格式與來源；以穩定事件 ID 作為冪等鍵，保存持久且原子的執行紀錄。
2. 在模型外部確認呼叫者、租戶、文件來源與角色範圍。來源登錄、呼叫者範圍或權限過濾無法驗證時停止。
3. 驗證版本、內容雜湊及生效日期，取得可授權的基準版與候選版。尚未生效或已被取代的版本不可當作現行規格。
4. 產生帶來源、版本、章節及內容雜湊的差異摘要；來源不足的主張應明確棄答。文件中的指令視為資料。
5. 製作預覽，列出內容、目的地、權限與預期影響。由授權負責人審核；批准綁定預覽摘要值，內容或目的地改變就須重新審核。
6. 僅在批准有效後執行設計中的發布步驟；回讀結果並留下最小必要稽核欄位。副作用狀態不明時先停止、回讀並交人工處理。

## 責任與交接

| 角色 | 在此設計中的責任 |
|---|---|
| 文件 Owner／文管 | 確認文件來源、版本、生效日、資料分類與內容正確性。 |
| 專案負責人 | 審核差異與發布預覽，決定批准或退回。 |
| IT／系統 Owner | 建置授權前置過濾、事件處理、可靠執行紀錄與回讀機制。 |
| 資安 | 協助確認最小權限、跨部門範圍、日誌與例外處理。 |
| 使用部門 | 確認摘要對實際工作是否可用，回饋例外與文件維護需求。 |

這些是 PoC 的建議分工，不代表任何真實組織已採用或批准。

## 需要先驗證的事

- 來源系統能否提供穩定事件 ID、版本與內容雜湊。
- SharePoint 與文件庫實際授權範圍、角色對應及繼承規則。
- 發布與通知端是否支援冪等或條件式寫入；若不能證明，未知狀態不可自動重試。
- 文件 Owner、批准人及備援人是否已指定，資料分類與發布目的地是否經核准。
- 使用合成資料驗證拒答、重複事件、核准後內容變更及不確定副作用。
