# 工廠設備知識庫與地端檢索助手

設備故障排查時，工程師常需要在不同廠牌、版本的手冊中找代碼和規格。找到相似文字還不夠：**系統必須讓人查回原文、確認適用設備；證據不足時不能編造操作步驟。**

這份公開快照展示我如何把設備文件整理成可檢索資料，結合全文與語意搜尋、重排序、引用來源及保守的拒答機制。它是以**合成測試資料**整理出的部分程式碼，不包含未授權的原廠 PDF 或廠內資料。

## 現在能看到什麼

- **文件處理與檢索**：文件解析／切塊、SQLite FTS5、Qdrant Local、FastEmbed、檢索融合與重排序相關模組。
- **引用與驗證**：回答必須對應可檢查的文件證據；當條件、版本或來源不足時，回報無法確認，而不是提供不受支持的操作處方。
- **合成測試與歷史紀錄**：`tests/`、`reports/` 和架構文件保留早期 Local Mode 的測試材料。

公開版本已包含部分 Python 程式碼，**不是僅有架構圖**，但也不是私人主專案的完整或最新分支。

## 系統如何回答一個問題

```text
使用者輸入設備、型號、版本與問題
    ↓
代碼／關鍵字比對（SQLite FTS5）
    + 語意檢索（FastEmbed + Qdrant Local）
    ↓
結果融合與重排序
    ↓
核對來源、適用條件與證據
    ├─ 依據足夠：回傳附來源的摘要或診斷資訊
    └─ 依據不足：說明不確定之處並停止無根據的操作建議
```

這套設計的取捨是**先確保回答可追溯，再追求回答得完整**。不直接控制現場設備，不能取代 OEM 正式文件與工程師判斷。

## 在公開快照中閱讀與測試

建議先讀 `docs/` 中的架構，再查看 `adapters/retrieval/`、`core/` 與 `tests/`。早期 Local Mode 測試可依下列專案內既有檔案執行；部分套件與模型須自行安裝，成功與否仍取決於當前環境。

```powershell
python -m pytest -q -p no:cacheprovider tests/test_sprint2_qdrant.py tests/test_mvp1_retrieval.py tests/test_mvp2_structured_llm.py tests/test_sprint3_negative_safety.py
```

公開快照的測試案例、輸入語料和版本不應拿來代表私人後續分支的最新驗收。若需要比較結果，應先固定相同 Commit、相同語料與相同執行環境。

## 安全與使用限制

- 範例使用合成資料；曾用於私人測試的公開 OEM 手冊原檔不在此散布。
- 不連接、控制或寫入真實 PLC／SCADA；不宣稱已完成真實產線 OT 驗收。
- `ABSTAIN`／拒答是受控測試中的設計與觀察，不代表所有現場情境都不會發生模型錯誤。
- 私人後續 Web 工作目前以本機 `127.0.0.1` 為邊界；尚未完成多使用者企業部署、身分驗證與營運維護驗收。
- 具體來源與快照界線以 [PROVENANCE.md](PROVENANCE.md) 為準，其他較早報告保留作歷史資料。
